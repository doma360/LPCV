# LPCV Mobile

App React Native (Expo Router), une seule appli mais deux jeux d'écrans selon le rôle (Volume 4/7 du LPD) : `app/(client)` et `app/(professionnel)`, séparés par `app/_layout.tsx` via `Stack.Protected`.

## Démarrage local

```bash
# L'API doit tourner (voir apps/api/README.md)
pnpm dev        # web, le plus rapide pour itérer
pnpm android    # émulateur/appareil Android
pnpm ios        # simulateur iOS
```

L'URL de l'API est déduite automatiquement de la machine qui fait tourner `expo start` (utile sur un appareil physique via Expo Go). `EXPO_PUBLIC_API_URL` dans `.env` peut la forcer — voir `.env.example`.

## État des écrans

Complets et testés en vrai (bienvenue → choix du profil → inscription/connexion → slides → recherche → demande avec photo → acceptation → en route avec position live → appel, avec les deux rôles) :
- `(auth)` : Bienvenue (un seul bouton "Commencer", pas d'autre lien), Choisir un rôle (deux cartes Client/Professionnel en couleurs pleines, inspirées d'Artisanpro CI — voir `docs/decisions.md`), Authentification (un seul écran par rôle avec bascule Connexion/Inscription façon Artisanpro CI — badge "Espace Client"/"Espace Professionnel", 16 métiers au choix pour un professionnel côté Inscription, Volume 1 §7 du LPD), Mot de passe oublié + Réinitialisation (code à 6 chiffres, provider mocké — voir `docs/deploiement.md`, redirige vers Authentification en connexion après succès)
- `(onboarding)` : slides de présentation affichées une seule fois, juste après une inscription (pas après une connexion) — "Passer" ou parcourir jusqu'au bout mènent au même endroit
- Client : **Accueil** (vrai tableau de bord — bandeau jaune plein en en-tête avec logo LPCV réel + wordmark + bouton cloche (ouvre Notifications, écran réel mais vide — pas de faux contenu tant qu'aucun système de notifications n'existe), salutation en dessous sur fond normal, champ "Ma position" tapable (chevron, relance la géolocalisation), carrousel de promos LPCV `src/components/PromoCarousel.tsx` (défilement automatique toutes les 4s, swipe manuel toujours possible), mini-carte de position `src/components/MiniCartePosition.tsx` avec bouton de recentrage, formulaire à 2 champs "Ma position"/"Métier recherché" avec suggestions qui lance directement le matching, "Vos demandes en cours" avec les demandes/réservations actives), **Rechercher** (sous-écran de résultats atteint après soumission du formulaire de l'Accueil — matching géolocalisé inchangé, résultat → **fiche détail unique par professionnel** plutôt que directement un formulaire — présentation, tarif indicatif, portfolio, disponibilités à titre informatif, avis, puis l'action "À domicile" (le bouton "Chez le pro" existe dans le code mais est retiré de l'écran, réservation mise en cache — voir `docs/decisions.md`)), Demander (formulaire de demande à domicile — description + photos), Mes demandes (liste des demandes de déplacement — distance du professionnel affichée en temps réel pendant "en route", relance automatique de la recherche sur le même métier si le professionnel refuse, avis à laisser une fois une demande "Terminée"; l'onglet Réservations existait mais est retiré, écrans intacts), Profil (avis laissés), Paramètres (infos du compte, changement de mot de passe, notifications, déverrouillage rapide, désactivation du compte)

  Trois passes sur cet écran le 23/08 (voir `docs/decisions.md`) : (1) grille de métiers directement sur l'accueil, jugée trop proche d'un écran de recherche ; (2) séparation Accueil (dashboard)/Rechercher (sous-écran), avec une grille "Accès rapide" ; (3) grille retirée au profit d'une mini-carte de position (simulation visuelle, pas de vraies tuiles — voir plus bas) et d'un formulaire à 2 champs qui lance le matching directement, sans étape de sélection de métier séparée. La bascule Déplacement/Réservation posée le 22/08 reste abandonnée au profit de la fiche détail unique. L'espace "Découvrir" reste documenté dans `docs/decisions.md` mais **volontairement pas construit**, n'apparaît nulle part dans l'app, le produit reste sur le périmètre du cahier des charges.
- Professionnel : Demandes reçues (devenu l'écran "dashboard" du pro — bande de chiffres clés en haut : demandes actives, total gagné, note moyenne ; bouton hamburger qui ouvre `ProSidebar`, un tiroir de navigation regroupant Modifier le profil/Paramètres — Réservations/Portefeuille retirés du tiroir, réservation mise en cache, Carte membre retirée du tiroir car intégrée directement sur Profil, voir `docs/decisions.md` — `ProSidebar` utilise le composant générique `src/components/Sidebar.tsx` (le côté client a sa propre barre d'onglets avec cloche de notifications, plus de tiroir client)), accepter/refuser, avancer le statut, appeler, envoi automatique de la position pendant "en route", Disponibilités (ajouter/supprimer des créneaux), Revenus (total gagné + historique), Réservations et Portefeuille (écrans toujours présents dans le code, plus atteignables depuis la navigation — voir `docs/decisions.md`), **Profil** (carte membre visuelle format paysage `src/components/CarteMembreVisual.tsx` avec photo du pro en avant, statut de vérification, note, puis directement sur la page : N° membre, membre depuis, statut d'abonnement avec dates et "expire dans X jours", QR de vérification — plus d'écran "Carte membre" séparé, tout est sur Profil, voir `docs/decisions.md` — puis portfolio de réalisations, avis reçus), Modifier mon profil (présentation, tarif indicatif, zones d'intervention — sans quoi le professionnel n'apparaît dans aucune recherche client ; case "J'ai un local" existe dans le code mais est retirée de l'écran, réservation mise en cache), Paramètres (même écran que côté client)

**Refonte visuelle "step by step" terminée (24/08)** : les 10 écrans restants (Rechercher, Mes demandes, Demander, Profil côté client ; Demandes reçues, Disponibilités, Revenus, Profil, Modifier le profil, Carte membre côté pro ; Paramètres, partagé) ont tous été repris pour partager le même langage visuel que l'Accueil livré en premier — badges pilule colorés pour les statuts, badges pastel avec icône pour les infos secondaires (distance, adresse, date), pastille jaune pour les prix, cartes avec ombre cohérente, boutons ronds avec ombre à la place des icônes flottantes, états vides avec icône plutôt qu'un texte gris seul. Seul `(auth)`/`authentification.tsx` reste dans son style d'origine, hors périmètre de cette refonte dès le départ (voir `docs/decisions.md`).

Verrouillage rapide (biométrie/PIN, `expo-local-authentication`) : activable depuis Paramètres, verrouille l'appli au démarrage et au retour au premier plan. Reste toujours déverrouillé sur web (pas de capteur), c'est le comportement attendu — à tester en vrai sur un appareil/émulateur avec empreinte enregistrée.

Barre d'onglets flottante personnalisée côté pro (`src/components/FloatingTabBar.tsx`) : fond noir arrondi, icônes seules (pas de libellé), petit indicateur blanc qui glisse au-dessus de l'onglet actif. Côté client (`src/components/ClientTabBar.tsx`, depuis le 23/08) : variante avec libellés visibles, pastille blanche pleine derrière l'icône active + faisceau lumineux dégradé au-dessus qui glissent ensemble (`Animated`, même technique, pas de dépendance supplémentaire) — choisi entre deux concepts envoyés par l'utilisateur (pastille+faisceau vs découpe qui fait "sortir" l'icône du contour de la barre, ce dernier bien plus coûteux à animer proprement en morphing de tracé SVG). Les deux remplacent la barre par défaut d'Expo Router via la prop `tabBar` du composant `Tabs`. L'écran Paramètres reste volontairement absent des deux barres (atteint depuis le bouton réglages du Profil). **Piège rencontré en ajoutant les libellés côté client** : toutes les routes du groupe `(client)` qui ne sont pas de vrais onglets (`demander`, `reserver`, `rechercher`, `notifications`, `pro/[id]`, `reservation/[id]`) sont bien présentes dans `state.routes` de React Navigation même sans être déclarées via `Tabs.Screen` — invisibles avec l'ancienne barre icônes-seules (pas d'icône = rien affiché), elles sont réapparues comme "onglets fantômes" dès qu'un libellé textuel a été ajouté. `ROUTES_MASQUEES` doit lister CHAQUE route non-onglet du groupe, pas seulement `parametres` — à vérifier si `FloatingTabBar` (pro) est un jour aussi passé en mode libellé.

`MiniCartePosition` (Accueil client) est une **simulation visuelle** (trame de grille + pin, pas de vraies tuiles) — le choix d'un vrai fournisseur (Google Maps ou Mapbox, chacun avec sa propre clé API et ses conditions de facturation) attend la validation de l'employeur, voir `docs/decisions.md`. `react-native-maps` n'a de toute façon pas d'équivalent web fiable, donc pas testable dans cet environnement de dev même une fois un fournisseur choisi — à vérifier sur un vrai appareil/émulateur le moment venu. Le suivi temps réel du professionnel pendant "en route" *fonctionne* déjà côté données, juste affiché en texte (distance) plutôt que sur une carte pour l'instant — même chantier de carte à brancher plus tard pour les deux usages. Passe design entamée sur le parcours d'entrée (Bienvenue/Choisir un rôle/Connexion/Inscription, hors périmètre de la refonte en cours) et l'accueil client — voir `docs/decisions.md`. Le reste des écrans garde encore le style minimal d'origine, repris un par un dans la refonte "step by step".

## Notes techniques

- **`expo-secure-store` ne fonctionne pas sur web** (API native Keychain/Keystore) — `src/lib/storage.ts` bascule sur `localStorage` uniquement pour la préview web de développement ; l'app cible réellement Android/iOS.
- **Metro plante avec `spawn EPERM`** dans cet environnement de dev sandboxé, qui refuse le spawn de processus enfants. `metro.config.js` force `maxWorkers = 1`.
- **`react` et `react-dom` doivent être strictement à la même version** pour le support web (`react-native-web`) — les deux sont épinglés à `19.1.0` dans `package.json`, ne pas les laisser dériver indépendamment.
- Si `expo start` plante immédiatement avec `TypeError: Body is unusable`, c'est un bug du "doctor" de la CLI Expo qui vérifie les versions en ligne — relancer avec `EXPO_OFFLINE=1` contourne le problème.
- **`useLocalisation` doit être un contexte partagé (`LocalisationProvider`), pas un `useState` local à chaque écran** — bug réel trouvé en split­tant l'ancien écran "Rechercher" en plusieurs écrans (Accueil, fiche pro, Demander) : la position choisie sur Accueil redevenait `null` sur l'écran Demander, chaque écran ayant sa propre instance du hook. Corrigé en `src/hooks/useLocalisation.tsx`, monté une fois dans `app/(client)/_layout.tsx` pour tout le groupe. À garder en tête pour tout futur état qui doit survivre à une navigation entre écrans distincts.
- **`<Modal animationType="fade">` de `react-native` ne se ferme jamais sur cet environnement de preview web** — confirmé en testant `Sidebar` (tiroir de navigation partagé pro/client) : `visible={false}` ne démonte pas le contenu tant que la transition CSS de fondu n'a pas fini, et cette transition ne se termine jamais ici car le panneau du navigateur ne compose pas d'images tant qu'il n'est pas affiché à l'écran (même cause que l'échec de `computer{action:"screenshot"}`). `animationType="none"` contourne le problème (le composant a de toute façon sa propre animation de glissement via `Animated`, redondante avec le fondu du `Modal`). Confirmé sans impact réel : testé une seconde fois via Playwright (vrai Chromium headless, pas le panneau intégré) — l'animation de glissement s'y joue normalement, `animationType="none"` reste quand même le bon choix puisqu'il évite de dépendre d'un comportement qui casse dans cet environnement de preview.
- **`Alert.alert` de `react-native` est un no-op silencieux sur web** (`react-native-web` ne l'implémente pas — confirmé dans son code source). Tout écran qui a besoin d'une confirmation testable en preview web (ex. désactivation de compte dans Paramètres) doit prévoir un repli `window.confirm` sur `Platform.OS === "web"`, le natif utilisant `Alert.alert` normalement.
